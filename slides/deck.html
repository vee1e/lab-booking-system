What it doesFour steps

One place to borrow and return lab equipment.

Sign in as a student, a teacher or the lab admin. The list shows what is free. Borrowing marks the item taken and sets a due day. Returning it closes the record and charges for any delay.

Class structure03
How they connectOwnership and links

The manager owns the lists. A booking stores two ids.

Owns

BookingSystem holds the items, the people and the records, and frees them when it closes.

Links by id

A Booking keeps a user id and an item id. Deleting an item cannot leave a broken link.

One way in

All changes go through BookingSystem. Nothing edits the lists directly.

A borrow writes one record and marks the item taken. A return closes the record and frees the item.
How they connect04
OOP ideasSix, each used in the code

Where each idea shows up.

Encapsulation

An instrument changes state only through borrow and return. Nothing outside sets it by hand.

Inheritance

Two bases, six types. Shared fields are written once in the base.

Polymorphism

One list call prints every instrument in its own format. The list never checks the type.

Abstraction

The base says what every item must do. It leaves the details to the child.

Overloading

Search works by word or by id, under the same name. Constructors come in two forms.

Shared ids

Each class counts its own records, so every new item, person and booking gets the next number.

Demo07
LimitsWhat is missing

What it does not do.

  • Nothing is saved. Items, people and bookings live in memory and reset when the program closes.
  • Dates are counted by hand. The day moves with one menu key, so there are no real dates.
  • One person at a time. It runs in a terminal, with no logins across machines.
Next
